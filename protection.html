3  Garbage collection and reference counting

3.1 GC

3.1.1 R_gc() (R_gc_running())

Trigger garbage collection, or check whether it is running.

void R_gc(void);
int R_gc_running();

Status: API · Header: R_ext/Memory.h · Protect: n/a · Errors: never · Since: — · R equivalent: gc

3.1.2 R_cycle_detected()

Detect a reference cycle between two objects.

Rboolean R_cycle_detected(SEXP s, SEXP child);

Status: non-API · Header: Defn.h · Protect: n/a · Errors: never · Since: — · R equivalent: —

You might wonder what all the PROTECT() calls do. They tell R that the object is in use and shouldn’t be deleted if the garbage collector is activated. (We don’t need to protect objects that R already knows we’re using, like function arguments.)

You also need to make sure that every protected object is unprotected. UNPROTECT() takes a single integer argument, n, and unprotects the last n objects that were protected. The number of protects and unprotects must match. If not, R will warn about a “stack imbalance in .Call”. Other specialised forms of protection are needed in some circumstances:

  • UNPROTECT_PTR() unprotects the object pointed to by the SEXP,

  • PROTECT_WITH_INDEX() saves an index of the protection location that can be used to replace the protected value using REPROTECT().

Consult the R externals section on garbage collection for more details.

3.2 Protect

3.2.1 Rf_protect() (Rf_unprotect())

Protect and unprotect objects from garbage collection.

SEXP Rf_protect(SEXP);
void Rf_unprotect(int);

Status: API · Header: Rinternals.h · Protect: n/a · Errors: never · Since: — · R equivalent: —

These are the functions underlying the PROTECT() and UNPROTECT() macros; package code should normally use the macros instead.

See also: PROTECT()

3.2.2 R_ProtectWithIndex() (R_Reprotect())

Protect an object at a fixed stack location so its value can be replaced later.

void R_ProtectWithIndex(SEXP, PROTECT_INDEX *);
void R_Reprotect(SEXP, PROTECT_INDEX);

Status: API · Header: Rinternals.h · Protect: n/a · Errors: never · Since: — · R equivalent: —

We sometimes need to coerce a protected value and place the new coerced value under protection. For these cases PROTECT_WITH_INDEX saves an index of the protection location that can be used to replace the protected value using REPROTECT. These are the functions behind those macros.

See also: PROTECT()

3.2.3 UNPROTECT_PTR() (Rf_unprotect_ptr())

Unprotect a specific object by pointer.

#define UNPROTECT_PTR(s) Rf_unprotect_ptr(s)
void Rf_unprotect_ptr(SEXP);

Status: non-API (use UNPROTECT()) · Header: Rinternals.h · Protect: n/a · Errors: never · Since: — · R equivalent: —

UNPROTECT_PTR() unprotects the object pointed to by the SEXP. It performs a search (from the top of the protection stack) to find the element to unprotect.

See also: PROTECT()

3.2.4 PROTECT() (UNPROTECT(), PROTECT_WITH_INDEX(), REPROTECT())

Protect SEXPs from garbage collection.

SEXP PROTECT(SEXP s);
void UNPROTECT(int n);
PROTECT_INDEX PROTECT_WITH_INDEX(SEXP s, PROTECT_INDEX *idx);
void REPROTECT(SEXP s, PROTECT_INDEX idx);

Status: API · Header: Rinternals.h · Protect: n/a · Errors: never · Since: — · R equivalent: —

PROTECT() pushes s onto the protection stack; UNPROTECT(n) pops the n most recent. Protections must balance within a single C call — they are released automatically when your .Call entry point returns, but unbalanced use inside a loop can overflow the pointer-protection stack. Use PROTECT_WITH_INDEX/REPROTECT when you must re-protect a different value at the same stack depth (e.g. in a loop).

SEXP out = PROTECT(Rf_allocVector(REALSXP, n));
// ... fill out ...
UNPROTECT(1);
return out;

See also: R_PreserveObject()

3.3 How PROTECT works

Objects protected by PROTECT() are placed on a protection stack (internally called R_PPStack), which itself is just an array of SEXPs. A protection index, called R_PPStackTop, denotes the top of the protection stack. When UNPROTECT()ing a (number) of objects, the stack top is decremented, and so all SEXPs ‘overflowing’ the R_PPStack are considered unprotected and hence eligible for garbage collection.

Note that this implies that PROTECT_WITH_INDEX() and REPROTECT() are merely APIs for modifying elements within the protection stack. UNPROTECT_PTR() performs a search (from the top of the stack) to find the element to unprotect.

3.4 Using PROTECT

Properly protecting the R objects you allocate is extremely important! Improper protection leads to difficulty diagnosing errors, typically segfaults, but other corruption is possible as well. In general, if you allocate a new R object, you must PROTECT it.

3.4.1 R_PreserveObject, R_ReleaseObject

3.4.2 R_PreserveObject() (R_ReleaseObject())

Preserve an object across C calls by adding it to R’s precious list.

void R_PreserveObject(SEXP);
void R_ReleaseObject(SEXP);

Status: API · Header: Rinternals.h · Protect: n/a · Errors: never · Since: — · R equivalent: —

The primary structure that R uses for protecting objects is the so-called R_PreciousList, which is just a pairlist of SEXPs; the R_PPStack protection stack is part of this list. These functions need to be used with care: because R_ReleaseObject() performs a recursive search for the object to release, inserting and later removing many SEXPs in the same order can cause performance regressions. See this dplyr issue for an interesting manifestation of this problem.

See also: PROTECT()

3.7 Reference counting

3.7.1 MAYBE_SHARED() (NO_REFERENCES(), MAYBE_REFERENCED(), NOT_SHARED(), MARK_NOT_MUTABLE())

Test or set an object’s reference-count flags before modifying it in place.

#define MAYBE_SHARED(x) (NAMED(x) > 1)
#define NO_REFERENCES(x) (NAMED(x) == 0)
#define MARK_NOT_MUTABLE(x) SET_NAMED(x, NAMEDMAX)
#define MAYBE_REFERENCED(x) (! NO_REFERENCES(x))
#define NOT_SHARED(x) (! MAYBE_SHARED(x))

Status: API · Header: Rinternals.h · Protect: n/a · Errors: never · Since: — · R equivalent: —

You must be very careful when modifying function inputs. These macros test the NAMED reference count so you can tell whether an object may be shared before changing it in place.

See also: Rf_duplicate()

3.7.2 IS_GETTER_CALL()

Test whether a call is a getter call in complex assignment support.

#define IS_GETTER_CALL(call) (CADR(call) == R_TmpvalSymbol)

Status: non-API · Header: Defn.h · Protect: n/a · Errors: never · Since: — · R equivalent: —

Complex assignment support: a temporary definition that will need to be refined to distinguish getter from setter calls.

You must be very careful when modifying function inputs. If you’re working with lists, use shallow_duplicate() to make a shallow copy; duplicate() will also copy every element in the list.

3.7.5 Internals

3.7.6 OBJECT() (MARK(), TYPEOF(), NAMED(), REFCNT(), SET_OBJECT(), SET_TYPEOF(), SET_NAMED(), LEVELS(), SETLEVELS())

Read and write the general attribute flags of a cons cell.

int  (OBJECT)(SEXP x);
int  (MARK)(SEXP x);
int  (TYPEOF)(SEXP x);
int  (NAMED)(SEXP x);
int  (REFCNT)(SEXP x);
void (SET_OBJECT)(SEXP x, int v);
void (SET_TYPEOF)(SEXP x, int v);
void (SET_NAMED)(SEXP x, int v);
int  (LEVELS)(SEXP x);
int  (SETLEVELS)(SEXP x, int v);

Status: API · Header: Rinternals.h · Protect: n/a · Errors: never · Since: — · R equivalent: —

General cons cell attributes: the object flag, GC mark, type, named count, reference count, and general-purpose levels. OBJECT() and SET_OBJECT() are not part of the API; prefer Rf_isObject() and Rf_setAttrib() (or CLEAR_ATTRIB(), added in R 4.5.0) in new code. SET_TYPEOF() will also not be available to packages in the future; use a constructor such as Rf_allocLang() (added in R 4.4.1) instead.

See also: Rf_isObject(), Rf_getAttrib()
